## AMB-09 - Scope of the §9 side adjustment: directional price features (Task 9)

- Spec: §9 "Side adjustment. Carry-direction features are multiplied by -s, so that positive means favourable to the candidate's side. A side indicator is included."
- Literal text: only "carry-direction" features are multiplied by -s.
- Options: (A, literal) side-adjust only funding / premium (carry-direction) features; F10 momentum (24 h / 7 d / 30 d returns, 7 d residual return) and F11 BTC 30 d return stay un-adjusted. (B) side-adjust every signed directional feature (x +s for price returns so positive = favourable to the side, or equivalently x -s under a sign convention), which is what "positive means favourable to the candidate's side" suggests for price direction.
- Consequence: both sides are fitted by one model per horizon. Under (A) a linear model sees the same F10 / F11-BTC value for the long and the short candidate of a symbol; its coefficient therefore pushes both sides' scores in the same direction, and the additive side indicator cannot undo that (it only shifts the intercept by side; it cannot flip the sign of a slope). A linear model thus cannot use directional price information (e.g. "positive momentum favours longs") at all. LightGBM can (via splits on side), so (A) also tilts the A2-vs-A3 comparison.
- Classification: **normative amendment required - user decision.** Whether every signed directional feature is side-adjusted is a methodology choice the spec text does not make; it is not an implementation detail.
- Code now (luna/v7/features.py CARRY_DIRECTION): the literal reading (A) - controller ruling, fix round 1 of Task 9 - until the user decides. Switching to (B) is a one-line change of CARRY_DIRECTION plus a sign convention for price returns.

- (a) **Layout.** `RawStore(root)`: one directory per table (`bars_last_15m` R3, `bars_last_1m` R5, `bars_mark_15m` / `bars_index_15m` / `bars_premium_15m` R4, `funding_archive` / `funding_rest` = the two R2 sources), one file per (symbol, calendar month): `<table>/<SYMBOL>/<SYMBOL>-<YYYY-MM>.parquet`. - (b) **Encoding and size (implementation parameters; fix round 1).** Parquet, zstd level 9, no dictionary (`FORMAT` = `parquet/zstd-9/scaled-int-delta/v1`). Every bar price / volume column (o, h, l, c, vol_base, vol_quote, taker_buy_quote; R4 o, h, l, c) is stored as int64 = value x 10^k with `DELTA_BINARY_PACKED`; k is per column per chunk: the largest number of significant decimals in the source CSV strings (`ingest._decimals`; the maximum over the monthly and daily files), or, for a frame without source strings, the smallest exact k <= `MAX_SCALE` = 12. At write the store verifies that `int / 10**k` reproduces every float64 value bit for bit (fix round 2: compared as int64 bit patterns, so -0.0, which no int reproduces, keeps the column float64); if any value fails (or k is unknown), that column of that chunk is stored as float64 (`BYTE_STREAM_SPLIT`). `open_ts`, `n_trades` and the funding integers use `DELTA_BINARY_PACKED`; the funding floats stay float64. The scales are written to the parquet schema metadata (`luna.v7.scales`) and to the manifest entry (`scales`), and the loader checks they agree. `content_sha256` is defined on the float64 values, so the encoding is not part of the content identity. All 9 R5 columns are kept. Measured on the reviewer's BTC-like 1m month (tick 0.1, clustered volatility and activity, volumes to 3 / 5 decimals; 44,640 rows): **20.2 B/row** on disk (float64 + zstd: ~34-47 B/row); full-month decode ~8 ms (all columns) / ~3 ms (one column). The R5 1m W_DEV store (~0.75 G rows) is therefore ~15 GB on synthetic data: still **flagged** against the ~10 GB budget until measured on real months (real volumes / prices usually compress better).
- (c) **known_at.** Not stored: it is the archive fixed-offset rule (`data.schema.KNOWN_AT_OFFSET_NS`: open_ts + 15 min for R3 / R4, + 1 min for R5), applied by the loader to every returned row; `put_chunk` refuses a frame whose supplied `known_at` differs from the rule (never silently dropped). The table manifest sha256 is the DT4 data-manifest hash (`RawStore.manifest_sha256s()` -> `runrecord.run_record(data_manifests=...)`); it covers every file through the symbol manifests (two levels because rewriting one ~33k-entry JSON per written chunk would cost ~TB of I/O at the R5 scale). One writer per store: every read-modify-write of the manifests holds a non-blocking OS lock on `<root>/.writer.lock` (`StoreBusy` otherwise; released by the OS if the writer dies). Chunk files are written once: temporary name, fsync, then a hard link (Windows without link support: a rename) to a target that must not exist, so an existing file is never overwritten (`ImmutabilityViolation`); the temporary file is removed in every case. `content_sha256` decides identity: identical content = no-op (the first manifest entry is kept), different content = `ImmutabilityViolation` (an `IntegrityBlocker`), K9-logged with rule "§3 raw files immutable once written (integrity)".
